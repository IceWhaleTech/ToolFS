# ZimaOS RBAC v1 —— 业务需求与技术实现的对齐说明

> 状态：设计稿阶段（依据业务需求 v0.3，2026-08-07 会议收敛）· 日期：2026-08-13
> 定位：把业务侧的权限模型翻译成三个服务各自要做的事，并列出阻塞项
> 关联：业务需求 `ZimaOS RBAC 业务需求 v0.3`；ToolFS 技术方案 [`design-rbac-snapshot.md`](design-rbac-snapshot.md)

权限模型横跨 **ZimaOS-UserService**（身份）、**IceWhale-Files**（授权存储与路径语义）、**ToolFS/toolfsd**（执行）三方，因此单独成篇，而不是塞进任一方的设计稿。

---

## 0. 实现后的变化（2026-08-14）

授权已在 UserService 落地，实现过程推翻了本文若干处判断。**下文各节保留原样**，因为它们记录了一次真实的判断变更；本节是与实现不一致处的清单。权威说明见 UserService 仓库的 [`docs/rbac-design.md`](../../ZimaOS-UserService/docs/rbac-design.md)。

**授权存储不再在 IceWhale-Files。** 权威源是 UserService 的关系元组表；`shares_model_dbs` 降级为 UserService 写出的投射，SMB 配置生成不变。上文「IceWhale-Files（授权存储与路径语义）」应读作「IceWhale-Files（SMB 投射与路径语义）」。

**删除维度不再只对 Agent。** `path` 命名空间对所有主体有 `read` / `write` / `delete` 三个关系。但**投射到 SMB 是有损的**：一条共享行每个用户只有一个 `read_only` 标志，且本设备 Samba 跑在 `nt acl support = no` 下，第三档既存不下也执行不了。所以 delete 只在 HTTP 与 ToolFS 通路上生效，经 SMB 访问的人受读/写约束。§1 里「与 Samba 能表达的一致」的收敛动机仍然正确，但结论从「用户侧不设删除」改成了「删除存在，但 SMB 通路上表达不出来，必须在提供该权限的地方写明」。

**应用可见性不再是「展示层」。** 它是 `app` 命名空间的一等关系，与 `visible` / `launch` / `manage` / `uninstall` 构成蕴含链。它与数据授权仍然正交——这一点没变。

**新增 `system` 轴**：terminal / settings / network / app.install。业务需求 v0.3 里没有它，是后续补充的要求。

**模型换成了 Zanzibar 关系元组**，而不是本文假设的「主体 × 路径 × 操作」平表。原因是需要组与任意间接层（组、目录继承、应用代用户代理、跨设备共享）。快照 + generation 订阅的契约形态未变，正是本文 §1 就确定的那一套。

**仍未解决**：IceWhale-Files `CheckPermission` 的 admin 放行（本文 §3.1 要求移除）。摘掉它需要先决定 Owner 默认持有哪些根目录——管理员目前不持有任何 share 行，提前移除会把他们锁在门外。

## 1. 统一权限模型

```
用户主体（Owner / Member） × 路径 × 读 / 写          ← 与 Samba 能表达的一致
Agent 主体                 × 路径 × 读 / 写 / 删     ← 删除收敛只对 Agent
```

删除维度**只对 Agent 存在**（§3.5）。它的存在理由本就是「ZimaOS 可写即可删是 agent
误删风险的根源」，因此限定在 agent 身上与其动机一致，也让用户侧授权与 Samba
的表达能力对齐。

**应用可见性是展示层**，与数据授权正交：能看到哪些应用由设置控制，能读到什么数据只由上式决定。

**「应用下的目录」就是目录。** Blue 的 workspace/document、Photos 的相册，实际对应的都是目录或文件。因此授权对象始终是路径，**不引入应用维度** —— 这也解答了业务文档待确认 #4（相册/Topic 的映射粒度）：映射是恒等的，不需要新抽象。

### 1.1 主体

| 主体 | 与 ZimaOS 现状的映射 | 授权来源 |
|---|---|---|
| **Owner** | ≈ 现有 `role=admin` | 显式授权行。**不是**特权放行 —— 见 §3.1 |
| **Member** | ≈ 现有 `role=user` | 显式授权行；默认零权限（仅默认数据路径 + 私人空间） |
| **Agent** | **新增主体类型** | 默认继承其 Member 的全部授权，可被 Member 收窄 |

**Zima Agent 与 ZimaOS 是同一套账号体系**（v0.3 明确）。Agent 不是独立登录体系，它是某个 Member 名下的程序主体。

### 1.2 Agent 的继承与收窄

```
Agent 的授权 ⊆ 其 Member 的授权
```

两个维度都可收窄，且**只减不增**：

- **路径收窄**：Agent 可只拿到 Member 授权路径的一个子集
- **操作收窄**：可关闭写 / 删；**删除默认关闭**，需显式开启

只读授权**永远**不能被提升为可写或可删 —— 无论 Agent 配置成什么。

### 1.3 私人空间与可见性

- 每个 Owner / Member 默认拥有私人空间，仅本人可见，可显式共享
- 创建成员时由 Owner 决定其空间可见性；家庭场景可开启「对 Owner 隐藏」
- **Owner 默认全量访问，显式隐藏的空间除外**

最后这条有一个关键的技术含义，见 §3.1。

### 1.4 应用可见性 —— RBAC 的第二根轴

业务模型里「应用可见性」与「目录授权」并列。v1 中它只是**展示层**（能看到哪些应用由设置控制），但方向上它会成为 RBAC 的一个正式维度：不同角色看到不同的应用集合。

模型形状上，它是与路径授权**并列的另一种关系**，而不是路径授权的一个维度：

```
主体 × 路径 × 读/写/删      ← 数据授权（ToolFS 执行）
主体 × 应用 × 可见/不可见    ← 应用可见性（需要另外的执行点）
```

这也是为什么**数据授权不引入应用维度**（见 §1 开头）：两者是两根轴，不是一根轴上的两个字段。把应用塞进路径授权，会让同一个目录对不同应用产生不同权限，而 SMB 侧根本没有应用概念，那条通路将无法表达。

**必须区分「可见性」与「访问控制」。** 从启动器里隐藏一个应用，并不阻止用户通过别的方式读到该应用的数据 —— 网页直链、SMB、或另一个应用。因此：

- 可见性需要**自己的执行点**（应用启动器 / 网关 / 应用运行时），**ToolFS 管不了它** —— ToolFS 执行的是数据访问，不是界面呈现
- 两根轴要么保持一致（隐藏应用时同步收回其数据目录授权），要么明确承认二者独立
- 如果只做可见性而不动数据授权，那它就是**防呆而非防护**，文档与 UX 都应如实呈现，不能让管理员误以为「隐藏了就是禁止了」

v1 不做这一轴的强制，但模型定型时应给它留出位置：授权服务应当能同时提供这两种关系，而不是事后再补一套并行的存储。

## 2. 与 ToolFS 现有实现的对照

### 2.1 业务需求验证了的既有决策（无需改动）

| 业务规则 | ToolFS 现状 |
|---|---|
| Agent 默认继承 Member，只减不增 | `AgentCapabilities` 正是这个模型 |
| Agent 删除默认关闭，需显式开启 | `AllowDelete` 默认 false，只读授权永不可提升 |
| 默认零权限 | 零授权即空视图，Owner 亦然 |
| 按用户授权，不设组、无组继承 | 逐行授权，无组概念 |
| 移动端与桌面端同一套模型（toolfs.d） | 业务文档已点名 toolfsd 为统一执行点 |

### 2.2 需要改造的部分

| # | 业务要求 | 现状 | 改造 |
|---|---|---|---|
| 1 | ~~读/写/删三层分别勾选~~ → **收敛为：用户读/写，删除收敛只对 Agent** | 授权只有 `read_only` 一个维度 | **不需要改存储**——现有 `read_only` 即够。Agent 从不经 SMB 访问，其删除收敛只由 ToolFS 执行。详见 §3.5 |
| 2 | Agent 可收窄路径范围 | `AgentCapabilities` 只做操作收窄 | 新增路径子集收窄 |
| 3 | Agent 是一等主体 | ToolFS 视其为「用户 + capability」 | 授权存储需支持「主体 = 用户 \| 该用户的某个 Agent」 |
| 4 | 授权即时生效（事件驱动） | TTL 30 秒轮询 | 见 §4 |
| 5 | 私人空间 | 无此概念 | 建模为自动创建的授权行 |

## 3. 上游必须完成的事项

> **原为四项，经「用户只给读/写」的收敛后减为两项**（§3.5）。

### 3.1 移除 `CheckPermission` 的 admin 放行

`IceWhale-Files/service/shares.go:618` 的 `CheckPermission` 首行是 `if role=="admin" { return true }`，不查表直接放行。

**业务要求「Owner 默认全量访问，*显式隐藏的空间除外*」，而特权放行根本无法表达「除外」。** 只要 Owner 短路返回 true，「对 Owner 隐藏」就是做不到的。

因此这条必须移除，Owner 的可访问范围改由显式授权行表达（系统在创建存储时自动为 Owner 写入，隐藏的空间则不写）。

> 这同时印证了 ToolFS 早已采取的立场：ZimaOS 自身在 admin 语义上是**分裂**的 —— SMB 侧数据驱动（`smb.go` 全文无 `admin`/`role`），Web API 侧特权驱动。ToolFS 选了 SMB 那一侧，现在业务需求也要求走这一侧。

### 3.2 ~~授权模型扩展为读/写/删三标志~~ → 已取消，见 §3.5

现有 `(samba_user, path, read_only, is_deleted)` 的单一布尔维度**保持不变**。

### 3.3 主体键支持 Agent

授权行的主体键当前是 `samba_user`，即一个 **Linux 用户名**。而 **Agent 不是 Linux 用户** —— 它是某 Member 名下的程序主体。

需要让主体可表达为「用户」或「用户的某个 Agent」。这会牵动 SMB 渲染（`smb.go` 按 `samba_user` 生成 `casa.%U.conf`）—— SMB 侧没有 Agent 概念，因此 Agent 的授权行**不应参与 SMB conf 渲染**，需要在渲染时按主体类型过滤。

### 3.5 收敛决策：用户只给读/写，删除收敛只对 Agent

> **状态：已定案。** 产品已确认接受「Member 无删除限制」（2026-08-13）。
> 因此本节不再是提案——用户侧授权就是读/写两级，share 表 schema 保持不变。

**这条收敛消掉了原本四项阻塞里的两项。**

Agent 是唯一需要删除收窄的主体，而 **Agent 从不经 SMB 访问** —— SMB 客户端是持
samba 账号的人。因此 Agent 的授权行永远不需要投射进 samba 配置：

```
用户授权 (Owner/Member × 路径 × 读|写)  → 渲染进 casa.%U.conf   ✓ SMB 能表达
Agent 授权 (Agent × 路径 × 读|写|删)     → 只由 ToolFS 执行      ✓ 不碰 SMB
```

**消掉的两项**：share 表无需扩展为三标志（现有 `read_only` 即够）；SMB 无需启用
NT ACL，也不会出现「同一份授权在不同通路行为不同」。

**已接受的代价**：

- 丢掉「Member 可写但不可删」的能力，例如「儿童账号能写作业但不能删家庭相册」。
  缓解：SMB 侧已有回收站（`recycle:repository`），ToolFS 侧有自己的回收站，
  **「误删可恢复」仍成立**——不成立的是「禁止删除」。这是「可恢复」与「不可为」的
  区别，**产品沟通与 UX 文案不能混同**。

**业务文档需随之修订**（业务侧动作）：

- §3.2「应用内用户权利统一为读/写/删三个层级」→ 用户侧为读/写两级；删除层级
  仅对 Agent 存在
- §6.2 的权限行示例 → Member 那行只应有「读/写」两列，去掉「删」
- §7 功能范围「统一目录授权（读/写/删三层）」→ 相应改写

**ToolFS 侧的连带改动**：对用户主体，写必须蕴含删（与 SMB 一致）；对 Agent 主体，
删另需 `AllowDelete`。因此判定逻辑必须知道当前主体是人还是 agent —— 这正是
§3.3「主体键支持 Agent」仍然必须做的原因。

```
用户主体：  写 ⟹ 读|列|建|改|删
Agent 主体：写 ⟹ 读|列|建|改，删另需 AllowDelete
```

否则会出现「用户经 SMB 能删、经 Photos 不能删」的反向不一致。

### 3.4 发布权限变更事件

业务规则要求「授权即时生效，变更无需重启或重新登录」，且口径确认为**事件驱动的真正即时**。

当前 ZimaOS MessageBus 只有 `samba:create-user-end` / `samba:delete-user-end`，**没有授权变更事件**。ToolFS 现在靠 TTL 30 秒轮询兜底，满足不了该要求。

需要在授权发生变更时发布事件，至少携带受影响的主体标识，供 toolfsd 立即重建该主体的视图。

## 4. 「即时生效」在 ToolFS 侧的缺口

上游给出事件之后，ToolFS 这边还有两处要改，其中一处是真实的架构缺口：

**① 视图无法在不重挂的情况下更新（架构缺口）**

`InstanceView` 是挂载时构建的不可变对象，`instanceRoot` 持有它的固定指针。授权变了，命名空间不会变 —— **必须重挂才能生效**。

代码注释里写着「a rebuilt view takes effect without remounting」，但**没有任何东西会去 rebuild 它**。需改为可原子替换的持有方式（`atomic.Pointer[InstanceView]`；`snapshotHolder` 已有同类实现可参照）。

**② 授权拉取从 TTL 轮询改为事件订阅**

保留 TTL 作为事件丢失时的兜底，但不再作为主要机制。

**好消息**：FUSE 侧的内核缓存已全部禁用（entry / attr / negative TTL 均为 0，内容走 direct IO），因此**快照一换，读路径立即生效**，不需要额外的 `NotifyEntry` / `NotifyContent` 调用。这是当初为「撤权不泄露陈旧数据」做的决定，此处顺带受益。

## 5. 授权链路上的既有缺陷（本次核实）

这两条与本次收敛无关，但会直接影响 v1 的正确性，应一并修复。

### 5.1 权限查询返回被放大的结果

`/v2_1/files/share/permission?username=X` **不过滤 `is_deleted`**，已禁用的共享会被当作有效权限返回。实测设备上 14 行 share 中 **8 行 `is_deleted=1`**。

**这不是理论问题**：`ZimaOS-UserService/service/user.go:916` 的 `getFilesPermissionUrl()` 默认正是返回这个端点，`GetUserPermissions` 直接转发。因此**今天任何经 UserService 查询权限的地方，拿到的都是放大后的集合**。

ToolFS 侧已自行过滤，但那是消费者的补救，不是修复。

### 5.2 权限写入存在丢更新

`UpdateUserPermissions`（`service/user.go:814`）的流程是：读取当前权限 → 计算 diff → 用 `errgroup` **并行**逐路径写回。

- 无乐观并发控制 → 两个管理员同时编辑会丢更新
- 无事务，跨 N 次 HTTP 调用 → 中途失败会留下部分写入，且无回滚

UX 旅程 B 是「勾选 → 保存即时生效」，这个写入路径需要先加版本号（或 ETag）做冲突检测。

## 6. 边界（v1 接受）

### 6.1 ToolFS 的隔离只在「经 ToolFS 访问」这条路上成立

**这是有意划定的范围，不是待补的缺口。**

ToolFS 保证的是：经它发起的操作受授权约束、可恢复、被审计。它**不加固平台** ——
`/DATA` 下的数据是 `0777`，任何本地进程、任何以非 root 运行的容器都能直接读写，
ToolFS 对此无能为力，也不声称能。

因此下列各项均在保护范围之外，v1 明确接受：

- **第三方容器应用可绕过路径授权** —— 业务侧 v1 接受，后续通过应用准入 + 身份透传 +
  容器隔离逐步收口
- **第三方应用内部账号与权限**不受 OS 控制
- **SMB / Files API / 其他服务的直接访问**不经过 ToolFS 的保护链

> 产品与 UX 必须如实呈现这一范围。把 ToolFS 的保护说成「平台级防误删」会造成
> 错误预期——它是 **agent 通路的防误删**。

### 6.2 SMB 在范围之外，但保护区仍需从 SMB 排除 —— 理由是健壮性，不是安全

既然 SMB 完全不在 ToolFS 的保护范围内，保护区 `.toolfs-state/` 的处理也要按**它真实的
性质**来说，不能夸大：

**它不是安全漏洞。** 回收站落在 Grant 根之下，而能经 SMB 看到该 Grant 根的人，本来就
对其下一切有访问权 —— 被删文件进回收站**没有暴露任何他原本看不到的信息**。嵌套 Grant
也不漏：只被授权 `Shared/subdir` 的用户，其 share 就在 subdir，看不到上层的保护区。

**真正的问题是另外两条：**

1. **SMB 用户可以删除或改坏保护区** —— 回收站与历史版本随之丢失，恢复能力被破坏。
   这是健壮性问题，而且后果不可逆。
2. **历史版本让旧内容留存得比原文件更久** —— 属于保留策略问题（`PurgeTrash` 尚未实现），
   不是访问控制问题。

**修法**：ZimaOS 已有现成机制，per-user conf 里本就渲染着

```
veto files = /.trash/ /.zima_encrypted_folders/
delete veto files = yes
```

在 `smb.go` 渲染处把 `/.toolfs-state/` 加进去即可；Files API 侧同样在遍历与列举时排除
该名字。**动机是防止误删保护区、以及避免它出现在用户的目录列表里**，不是防止数据被看到。

## 8. 授权应当收口到 UserService

**结论：是的，且「应用授权」这一需求把它从「可选优化」变成了「必须」。**

### 8.1 为什么是现在

此前评估「把权限从 IceWhale-Files 收口到 UserService」时，结论是**先修契约、暂不搬家**，理由是权限是路径作用域的，而路径是 Files 的领域 —— 搬走只是把耦合换了个方向。真正的搬家被放在一个条件后面：**当出现非路径型权限时**。

「授权指定用户访问某个 Docker 应用」正是这样一条权限：

- 它的对象是**应用**，不是路径
- 它与存储布局、public path 规则、路径别名**全都无关**
- 它在 Files 里**没有任何归属理由** —— Files 是文件服务，不是应用注册表

把它塞进 share 表，就是第二次犯「让一个服务持有它不该持有的领域模型」的错误。所以：**这条权限从第一天起就应该在 UserService**。

而一旦 UserService 要持有一根轴，「两根轴分处两个服务」就成了最差的形态 —— 权限的真相又变成两处。

### 8.2 收口成什么形状

关键是把**权威**、**存储**、**投射**三件事分开，而不是简单地把表搬走：

| 层 | 归属 | 说明 |
|---|---|---|
| **授权权威**（模型、写入、谁可授予谁） | **UserService** | 身份语义天然属于它；两根轴统一在此定义与写入 |
| **路径校验** | **IceWhale-Files** | public path 上界、别名归一、存储生命周期——这些仍是 Files 的领域。UserService 写入前调用它校验 |
| **投射到执行通路** | 各执行点 | SMB conf / Files 的 CheckPermission / ToolFS 挂载视图 |

**校验不等于拥有。** 我之前的顾虑是「路径语义属于 Files」，这条依然成立 —— 但它论证的是 Files 应当继续做**路径校验器**，而不是继续做**授权所有者**。这两者被我上次混在一起了。

### 8.3 SMB 的启动依赖如何解决

上次反对搬家的一条实质理由是：`smb.go` 在开机时从本地表渲染 `casa.%U.conf`，数据搬走就多了一个**开机关键路径上的跨服务依赖**。

解法是**投射而非直读**：UserService 作为唯一真相，向下发布一份**物化视图**（本地文件或本地库），SMB 与 Files 读这份物化视图，不在开机路径上调用 UserService。

这与 §3.4 要求的**变更事件**是同一件事的两端 —— 事件既驱动 toolfsd 重建视图，也驱动物化视图刷新。做一次，两个需求一起满足。

### 8.4 对 ToolFS 的影响：几乎没有

ToolFS 经 `PermissionProvider` 接口消费授权，换后端只需换一个实现。**无论最终收口到哪里，ToolFS 侧改动都很小** —— 这也反过来说明当初把它抽象出来是对的。

需要 ToolFS 关注的只有一点：如果应用可见性将来要**强制执行**（而不只是展示），那不是 ToolFS 能做的（见 §1.4）—— 它执行数据访问，不执行界面呈现与应用启动。

### 8.5 迁移的硬要求

1. **单写者**：迁移期间绝不双写。双写正是「第二套权限真相」的成因。
2. **契约先行**：ToolFS 已经是消费者，接口要先版本化再动数据。
3. **admin 语义先统一**（§3.1）：不先定这一条就收口，只是把不一致搬了个地方。
4. **迁移前后交叉校验**：对每个 `(主体, 路径, 操作)` 断言新旧判定一致，有分歧即阻断迁移。
5. **不要在同一批改动里既搬模型又改语义** —— 两件事叠在一起，出问题将无法定位。

## 9. 落地顺序建议

| 顺序 | 内容 | 为什么在这个位置 |
|---|---|---|
| **0** | 修 §5 的两个既有缺陷（`is_deleted` 过滤、写入并发控制）；把 `.toolfs-state` 加入 SMB veto 与 Files 排除（§6.2） | 都与模型改造无关、独立可做。§5.1 **正在放大权限**，§6.2 防止 SMB 用户误删保护区（健壮性，非安全） |
| **1** | 定型统一授权模型：两根轴、Agent 主体（§1、§3.3、§3.5） | 模型形状决定后面一切。**此时只定契约，不动存储**——按 §3.5 的收敛，存储 schema 本次无需改动 |
| **2** | 移除 admin 放行（§3.1） | 语义变更，**必须与模型改造分开一批** |
| **3** | UserService 成为授权权威（§8）；应用授权这根轴**直接建在 UserService** | 应用授权无历史包袱，是验证新模型的最低风险载体 |
| **4** | 路径授权迁移；Files 转为路径校验器；SMB/Files 改读物化视图（§8.3） | 依赖 1–3 全部就位，风险最高，放最后 |
| **5** | 变更事件（§3.4）与 ToolFS 视图热替换（§4） | 事件同时驱动物化视图刷新与 toolfsd 重建，与第 4 步同批做最省 |

两条贯穿始终的纪律：

> **不要在同一批改动里既搬模型又改语义。** 第 1 步改模型形状，第 2 步改 admin 语义 —— 叠在一起出问题将无法定位。
>
> **应用授权先行是有意的。** 它没有存量数据、没有 SMB 耦合、没有迁移风险，是检验「UserService 作为授权权威」这套形状是否成立的最便宜的一次实验。等它跑通了，再搬风险最高的路径授权。
