## 一、一句话

给 Zima Agent 一个**统一、可回退的文件访问通道**：agent 的所有文件操作经 ToolFS 拦截，误删可恢复、误改可回退、整个任务可撤销。

---

## 二、背景与目标

Zima Agent（基于 Codex 二开）直接操作用户文件，存在两类风险：

| 风险 | 说明 |
|---|---|
| **误删 / 误改** | agent 执行 `rm`、覆盖写之后无法恢复。prompt injection 场景下更严重 |
| **越权** | agent 可能访问不属于当前用户权限范围的数据 |

原始需求（workplan）：「用户1能看到 xxx 挂载目录，用户2能看到 xxx 挂载目录」，8 月第二周交付。

---

## 三、关键调查结论

**以下为在代码与真机（ZimaCube Pro / ZimaOS v1.7.0）上实测所得，所有决策建立在这些事实之上。**

### 3.1 ZimaOS 的文件权限在哪里

> **前两条已于 2026-08-14 被授权改造推翻。** 权威源移到了 UserService 的关系元组表，IceWhale-Files 的那张表降级为投射，代理已拆除。当前状态见 [`rbac-v1-alignment.md`](rbac-v1-alignment.md) §0。

- ~~唯一事实来源是 IceWhale-Files 的一张 SQLite 表~~，每行表达「某用户对某路径前缀有只读 / 读写权限」。
- ~~**UserService 里没有权限数据**，它的权限接口只是转发给 IceWhale-Files 的代理。~~
- **POSIX 文件权限完全不参与**：所有文件为 `root:root 0777`，SMB 侧配置为强制 root 身份。隔离 100% 依赖那张表。
- 新用户默认权限为零，必须管理员显式授权。
- **不存在 per-user home 目录**，所有用户共用一棵目录树。

### 3.2 ZimaOS 对 admin 的处理是分裂的

- **SMB 侧数据驱动**：admin 看到的就是他在表里的行，没有特权全盘。
- **Web API 侧特权驱动**：`role == admin` 直接放行一切，不查表。

实测：admin 在表里恰好有 3 条有效授权，与其 SMB 配置完全对应。

### 3.3 主存储没有快照能力

| 存储 | 文件系统 | 快照 |
|---|---|---|
| **`/DATA`（用户主数据）** | **ext4** | **不可能** |
| `/media/HDD-Storage`（数据盘） | btrfs | 可以 |

`/DATA` 是裸分区、不在 LVM 之上、ext4 无快照特性、不支持 reflink（已实测）。**这是能力上界，除非重装系统换文件系统，否则无法改变。**

连带影响：`/DATA` 上保存文件旧版本是全量拷贝（btrfs 盘上是零拷贝），而该盘已用 87%、仅剩 31G。

### 3.4 现有代码有三个可绕过访问控制的漏洞

均已写测试实际复现：路径穿越（在路径里加 `../` 即可读到挂载范围外的文件，审计还记为成功）、符号链接逃逸、只读挂载被绕过写入。另有并发数据竞态。

**不修这些，其上的任何访问控制都是装饰。**

### 3.5 Agent 的实际运行形态与权限

- **常驻 Web 服务 + 常驻 app-server**，codex 核心内嵌于 app-server 进程内；会话是进程内对象，**没有按任务的进程边界**。
- 容器虽以 privileged 声明，但**入口脚本在启动服务前已降权到普通用户**。实测 agent 进程零内核能力、无法挂载、无法读取块设备。
- **因此安全条件比预期更好**：只要 ToolFS 守护进程以特权身份运行，其保护区与挂载 agent 均无法触碰。

### 3.6 ~~agent 与 ZimaOS 是两套独立账号体系~~ → **已被推翻**

本方案长期把这条当作最关键的约束，并据此设计了账号绑定流程。**业务需求 v0.3
（2026-08-07）确认：Zima Agent 与 ZimaOS 是同一套账号体系。**

因此身份直接来自会话，**绑定问题不存在**；原决策 3 的三条绑定路线随之作废，
两个前置阻塞项（绑定方式、凭据续期主体）一并消除。

> 值得记录：这条前提曾被反复强调、被写进设计稿标为「不可再漂移」，最终仍然变了。
> 挡住这次冲击的是 `IdentityResolver` 抽象——接口没变，内部没动，只是实现退化为
> 「从会话直取身份」。

### 3.7 agent web 无鉴权暴露（独立于本方案）

实测：服务绑定在所有网络接口上，且无任何凭据即可读取会话数据。同网段任何人都能打开 agent、创建会话、驱使它读写用户文件。

**这与 ToolFS 无关、独立存在。** ToolFS 落地后能收窄「agent 能碰哪些目录」，但无法阻止未授权者驱使 agent。建议优先修复。

### 3.8 agent 具备无头浏览器能力，且资源占比远超 agent 本身

Chromium 已内置，按需启动，由一个独立的轻量管理服务负责，经两个工具暴露给 agent。**当前为每会话一个浏览器实例，profile 与登录态持久化。**

实测内存：

| | 内存 | 进程数 |
|---|---|---|
| agent 实例（app-server） | **152 MB** | 1 |
| **无头浏览器实例** | **645 MB** | **8** |
| 浏览器管理服务 | 6.4 MB | 1 |

**浏览器比 agent 实例贵 4 倍多**——容量规划的主要矛盾在浏览器，不在 agent。设备总内存 15.37 GB，按每用户一路会话约 800 MB 估算，理论上限约 18 用户，而机器上还运行着 23 个其他容器。

实测启动耗时：**7 秒是完整 agent 栈**（含浏览器管理、反馈、Web 服务）的数字；**实例容器只跑 app-server，实测 0.75–5.4 秒**。配合预热池后，用户可感知的分配延迟为 **136 毫秒**（见风险 7）。

### 3.9 codex 已把沙箱责任委托给外部

codex 的沙箱策略配置为「外部沙箱」——它明确不自行实施内核级隔离，而是依赖运行环境提供。这与 ZimaOS 内核未启用相关内核特性恰好相容，**也正是 ToolFS 应当填入的位置**。

## 四、核心决策与理由

评审重点。每条含**决策、理由、代价**。

### 决策 1：ToolFS 不定义权限，只消费 ZimaOS 既有授权并收窄

- **理由**：自建一套策略会造成**第二套权限真相**——管理员在 ZimaOS UI 改了权限 ToolFS 不知道，反之亦然。两边分歧即安全事故。
- **代价**：受限于 ZimaOS 现有模型的表达能力（只有「只读/读写」一个维度）。
- **ToolFS 的增量价值**：把「可写即可删」拆开，**删除权限默认不授予**——这正是 agent 误删风险的根源。

### 决策 2：每用户一个实例容器，由宿主侧编排 ⭐

**这是 per-user 权限落地的方式，依据源码调查与实测确定。**

对 codex 的调查表明：agent 是**常驻 Web 服务 + 常驻 app-server**，codex 核心内嵌于 app-server 进程内，会话是进程内对象——**不存在可被包装的按任务进程边界**。因此改为按用户拆分实例：

```
agentd（宿主）           拉起/回收实例容器
   ↓ 请求挂载点
toolfsd（宿主）          身份解析 → 拉授权 → 建挂载 → 返回路径
   ↓
agentd 拉起实例容器，把该挂载点 bind 进去
   ↓
Web 服务                 按用户把请求调度到对应实例
```

**承载身份的是挂载点**——它绑定了某用户的授权，决定可见与可写范围；实例通过被 bind 了哪个挂载点而受约束，**其自身对身份无感**。

- **codex 侧零改动**——原生支持独立配置目录与网络监听。
- **代价**：Web 服务需把单例改为按用户的实例池（实测 40 处调用点 / 12 个文件），并实现实例编排。**这部分工作量在 agent 团队，不在 ToolFS 工期内。**
- **顺带收益**：当前单实例意味着全部用户共享 codex 的记忆库，这本身即隐私问题，多实例一并解决。

### 决策 2.1：挂载在宿主完成后 bind 进容器

**挂载点结构是安全约束，不是部署细节。** 挂载确实先于容器建立，首次可见性无问题；但实例容器长期运行，会跨越 toolfsd 重启。实测发现——**若 bind 源就是 FUSE 挂载点本身，toolfsd 重挂后容器会静默读到旧挂载的数据**：管理员刚撤销的授权仍然生效，且无任何错误信号。

故规定：bind 源取挂载点的**父级普通目录**（FUSE 挂在其下一层），传播模式 **`rslave`**（禁 `rshared`——双向传播等于把挂载能力交还容器）。ZimaOS 上新建挂载默认继承 `shared`，无需额外配置。

> 这是一个**部署配置就能引入的安全回归**，须在编排组件的启动参数中固化并纳入验收。

**只 bind 需要的那一个目录**：

| 宿主上的路径 | 是否 bind 进实例 |
|---|---|
| 该用户的挂载点 | ✅ |
| 真实数据 | ❌ 容器内根本不存在 |
| 保护区（回收站 / 版本 / 审计） | ❌ 实例触及不到 |

比「挂进去再遮蔽」更彻底，也更不容易出错。

### 决策 2.2：共享目录的并发按「数据同源」处理，不做额外机制

多个用户可能对**同一目录**都持有读写授权（授权模型允许），此时两个挂载点指向同一份后端数据。

**需要澄清一个常见误解**：挂载点隔离的是**视图与权限**，不是**数据**。两个挂载都只是视图，数据在后端只有一份，读写在那里汇合——因此互相可见是天然的，**与挂载传播无关**。已用最小 FUSE passthrough 实测：两个独立挂载（不同 superblock）指向同一后端，写入 / 创建 / 删除双向即时可见。

真正需要处理的是另外两件事：

| 事项 | 处理 |
|---|---|
| **保护链协调** | 版本去抖与数量上限的判断必须跨挂载互斥 → **文件系统守护进程单进程服务全部挂载**（代价见风险 10） |
| **撤销冲突** | 已覆盖：撤销时若发现文件在此之后被他人改过，跳过该项并报告。**多用户并发是比「SMB 等其他通路」更高频的触发场景** |

**版本历史属于文件，不属于用户**——A 写入产生的旧版本，B 同样可据以恢复。按用户切分版本链会导致恢复时看不到完整历史。

### 决策 2.3：隔离由 runtime 保证，而非配置拼装 ⭐

**这是最容易被忽略、且失效时最无声的一环。**

若把多个实例放在同一容器内以进程形式运行，仅靠挂载视图**不足以隔离**：系统提供了一条旁路，一个进程可通过 `/proc` 读取另一进程的根目录、当前目录与已打开文件——**条件仅是两者同属一个系统用户**。

**实测确认**：当前容器内，同为同一用户的两个进程之间可完整读取对方的这些内容。若所有实例都以同一用户运行，隔离将**退化为统一挂载**，只是需要绕一下。

改用独立容器后此问题**天然消除**——不同容器不共享进程视图。隔离由 runtime 默认保证，不依赖实现纪律。

（曾评估的「在 agent 容器内启动子容器」已排除——那需要把容器管理接口暴露给 agent，等同赋予其逃逸能力。）

### 决策 2.4：容器不再需要任何特权

| | 当前 | 本方案 |
|---|---|---|
| agent 主容器 | 特权模式 | **无需任何特权**（纯调度服务） |
| 实例容器 | —— | **无需任何特权**（只拿到一个 bind 进来的目录） |
| 容器管理接口 | —— | 仅宿主侧组件使用，**不暴露给任何容器** |

**代价**：实例容器冷启动 0.75–5.4 秒（同容器进程形态为 422 毫秒，但该形态已因隔离不可靠被排除，见决策 2.3）。**已用预热池把这项代价基本消除**——预热容器空转仅 2.4 MB，分配延迟 136 毫秒（见风险 7）。

### 决策 2.5：职责边界

建议**编排与文件系统分离**：

| 组件 | 职责 | 不需要知道 |
|---|---|---|
| `toolfsd` | 身份解析、授权、挂载、保护链、审计 | 容器 |
| `agentd` | 实例容器的拉起、回收、资源限额 | 文件系统 |
| Web 服务 | 按用户调度 | 挂载与权限 |
| 实例 | 执行任务 | **身份** |

两个特权互不耦合，且该边界正好对应团队边界。**ToolFS 的交付物因此收敛为一个清晰接口——「给定用户身份，返回一个受该用户授权约束的挂载点」。**

### 决策 3：账号绑定——短期映射表，目标轻量授权流程 ⭐

因两套账号体系独立（事实 3.6），必须显式建立对应关系：

```
agent 账号  →  ZimaOS 授权主体
```

ZimaOS 侧目前只有「用户名密码登录」，**没有第三方授权流程**，因此有三条路：

| | 做法 | ZimaOS 改动 | 评价 |
|---|---|---|---|
| A | 用户在 agent 内输入 ZimaOS 密码 | 无 | **不建议**：应用收集平台密码属反模式 |
| **B** | agent 跳转 ZimaOS 确认页 → 用户确认 → 回调换凭据 | 需新增端点 | **正确终态**。同设备单一可信客户端，无需完整 OAuth |
| **C** | 管理员配置映射表 | 无 | **短期方案**：零协议设计、立即可用，但需手工维护 |

**关键设计：ToolFS 侧用一个身份解析抽象把三种方案隔离在同一接口后，因此绑定方案的选型不阻塞 ToolFS 开工。** 过渡期可先让全部实例绑定一个专用 ZimaOS 账号（建议新建而非复用 admin——admin 的授权由系统自动写入全部存储根读写权，等同不设限）。

此时已具备**完整的误删保护**与 **agent 整体的权限约束**，仅缺用户间隔离。

### 决策 4：建议将浏览器拆为独立服务并改为按用户复用 ⭐

**这不是 ToolFS 的必需项，但它决定多实例方案的内存是否可控**，故一并提出。

浏览器管理服务**已具备独立服务的全部特征**：独立进程、绑定所有网络接口、完整 REST 接口、客户端经代理层解耦、**服务地址本就是环境变量**。因此拆分只需新增一个容器并改一个变量指向它，改动极小。

复用粒度建议**按用户而非按会话**：

- 「停止浏览器但保留 profile 与登录态供下次打开」的语义**已经存在**，机制现成，缺的只是空闲回收策略；
- 登录态本来就是按用户的，按用户分配语义自洽；
- 全局池化不可取——归还时不清理会泄露登录态，清理了又失去保留登录态的价值。

按 3 个并发活跃用户估算约 2.4 GB，在 15 GB 上宽裕。**若维持现状（每会话一个浏览器且无回收），一个用户开多个会话即会迅速耗尽内存。**

### 决策 5：能力按存储而异，如实暴露差异

- **理由**：`/DATA` 是 ext4，没有时间点快照（事实 3.3）。
- **决策**：不假装统一。系统对外声明每块存储各自具备什么能力，agent 与 UI 可查询。
- **代价**：产品说明与 UI 必须区分呈现，不能用统一的「文件历史」措辞掩盖差异——否则用户会基于错误预期丢数据。

### 决策 6：不做「copy 型快照」降级

- **理由**：全量拷贝在 TB 级数据上又慢又占空间，且拷贝期间数据仍在变化、拿不到一致时间点。它想解决的误删场景已被回收站与文件版本覆盖，而后两者代价极低。
- **决策**：非 btrfs 存储明确声明「不支持快照」，而不是提供一个看起来能用、实际会拖垮系统的降级实现。

### 决策 7：快照与闪回分权

- **理由**：文件系统快照的粒度是整个存储卷，而权限的粒度是路径。若允许普通用户执行整卷回滚，一个用户的回滚会覆盖所有人的数据。
- **决策**：**快照 = 系统级只读时间点（仅管理员）；闪回 = 用户级、受当前权限约束的写回**。整卷回滚限定为管理员 + 离线 + 二次确认 + 自动前置快照。

### 决策 8：会话级撤销是 agent 场景的核心能力 ⭐

- **观察**：agent 的高频需求是「把刚才那个任务做的事整体撤掉」，而不是「回到昨天下午三点」。备份类产品提供的恰是后者。
- **决策**：提供**按任务整体撤销**——agent 一个任务动了 15 个文件，一条指令全部回退。
- **关键价值**：该能力建立在回收站与文件版本之上、**不依赖 btrfs**，因此在 ext4 的 `/DATA` 上同样可用——正好补上「主存储无快照」的缺口。

### 决策 9：不依赖、不对接 backup 模块

- **理由**：ToolFS 服务的是 **agent 操作安全**，不是灾备。两者的粒度、时效、使用场景都不同。
- **代价**：`/DATA` 上不提供跨盘的时间点恢复。

### 决策 10：admin 在文件访问层没有特权

- **理由**：ZimaOS 自身分裂（事实 3.2）。ToolFS 选择**数据驱动**那一侧——admin 与普通用户走同一套逻辑，系统内不存在「管理员绕过检查」的代码路径。
- **实证**：admin 的授权本就由系统自动写入，按表构建后**实际可见范围不变**，但权限变成显式、可审计、可收窄。
- **代价**：无。角色仅用于管理操作（清空回收站、快照、回滚）的准入。

### 决策 11：路径安全必须最先做

- **理由**：事实 3.4 的三个漏洞使任何访问控制可被一行 `../` 穿透。
- **决策**：作为 P0 最先交付，**不可跳过、不可与其他工作并行绕开**。

## 五、交付内容

| 能力 | 说明 |
|---|---|
| **路径安全加固** | 修复穿越 / 软链逃逸 / 只读绕过 / 并发竞态 |
| **身份与授权** | 解析 agent 账号对应的 ZimaOS 授权主体，据其授权构建挂载视图 |
| **按用户的挂载视图** | 用户 A 只见 A 被授权的目录，用户 B 只见 B 的——**直接满足原验收标准** |
| **实例隔离** | 每用户一个独立容器，挂载、进程、网络视图均由 runtime 隔离；数据、会话、记忆互不可见 |
| **回收站** | 删除不是真删，可恢复 |
| **文件版本** | 覆盖写之前保留旧内容，可回退；带排除规则（见风险 2） |
| **会话级撤销** | 按任务整体撤销一串操作，冲突项跳过并报告 |
| **查询与恢复接口** | agent 可查「这个文件能回到哪些时间点」并执行恢复 |
| **完整审计** | 所有变更落盘，含真实用户身份与恢复凭据 |

**不含**：btrfs 快照（可选增强，仅数据盘生效，可独立排期）。

## 六、能力边界（诚实声明）

**必须写进产品说明，不能宣称不存在的保证。**

| 范围 | 保证 |
|---|---|
| 挂载点内的操作 | **完整 RBAC**：只见授权目录、删除权限默认不给、审计记真实身份 |
| 实例之间 | **独立容器**，挂载 / 进程 / 网络视图由 runtime 隔离；对方的挂载路径在本容器内**根本不存在** |
| 真实数据与保护区 | **不进任何容器**——回收站、版本、审计位于实例触及范围之外 |
| 实例主动绕过 | 实例容器**零内核特权**：无法挂载、无法访问块设备。当前设计下无已知可行绕过路径 |
| 主数据的时间点快照 | ❌ 主存储是 ext4，能力上界，不可能 |
| 其他通路（SMB / 容器等） | ❌ 不经过 ToolFS，不受保护 |
| 未授权者驱使 agent | ❌ 需 agent 自身的鉴权，超出 ToolFS 范围 |

> 前四项以 **`toolfsd` 与 `agentd` 运行在宿主**为前提。若回退到「同容器内多进程」形态（已排除），隔离将退化为依赖多项配置拼装，且 `/proc` 穿透风险重现（决策 2.3）。

## 八、主要风险

| # | 风险 | 应对 |
|---|---|---|
| 1 | **当前 agent 容器为 privileged** | 本方案下实例容器**零特权**（挂载在宿主完成后 bind 进去）。现有主容器的 privileged 声明可一并收窄——实测入口脚本已降权，特权未传导到 agent 进程 |
| 2 | **开发工具会淹没版本保护**：codex 驱动的 `npm install` 会产生数万文件，各存一份版本可在一次任务内打满仅剩 31G 的 `/DATA` | 默认排除 `.git/`、`node_modules/` 等不存版本，**但删除仍进回收站可撤销**。此项不可省略 |
| 3 | `/DATA` 空间紧张，版本保护是全量拷贝 | 大小上限按剩余空间动态调整；低空间时降级为「只保回收站」并告警 |
| 4 | 回收站不释放空间 | 默认启用定时清理，含容量与最低剩余空间阈值 |
| 5 | 其他通路（SMB/Docker）绕过 ToolFS 修改文件 | 明确声明保护范围仅限经 ToolFS 发起的操作 |
| 6 | 撤销时遇到「文件已被他人修改」 | 默认跳过并报告，不静默覆盖、也不因一处冲突废掉整次撤销 |
| 7 | ~~实例启动约 7 秒~~ → **实测后基本消解**：7 秒是完整 agent 栈的数字，实例容器仅 0.75–5.4 秒 | **预热池已端到端验证**：预热容器空转仅 2.4 MB，分配延迟 **136 毫秒**。硬约束是 slot **一次性使用、绝不跨用户复用**（否则残留数据泄露） |
| 8 | 宿主 rootfs 只读，部署宿主侧组件受限 | 借助可写分区或系统扩展；需在实施前确认可行 |
| 9 | FUSE 对小文件密集操作的开销（`git status` 要 stat 数千文件） | 应用层缓存权限判定结果，随授权变更整体失效。**注意**：放开内核缓存另需实现跨挂载失效——实测「A 新建的文件在 B 上持续不可见达一整个缓存周期」 |
| 10 | **文件系统守护进程是单点**（决策 2.2 的代价）：单进程服务全部挂载，崩溃会同时中断所有用户 | 自动拉起 + 重挂对容器可见 + 编排组件感知后回收实例。若运维不接受该影响面，可改为每挂载一进程 + 文件锁协调，接口不变 |
| 11 | **挂载点结构配错即引入安全回归**：bind 源若设成挂载点本身，重启后撤权静默失效（决策 2.1） | 在编排组件启动参数中固化，并纳入验收断言 |

## 十、建议的评审结论

1. **立即启动路径安全加固**（P0，无争议、无外部阻塞、所有方案共同前置）。
2. **就问题 6 拍板**——若接受过渡方案，只需改一个环境变量即可拿到完整误删保护，不必等账号绑定，这是最快兑现价值的路径。
3. **确认问题 1、2**——它们共同决定 per-user 隔离的落地时间，且工作量主要在 agent 团队一侧，宜尽早对齐。
4. **确认问题 3**——`agentd` 是本方案的落地前提，且宿主 rootfs 只读这一约束需尽早验证。
5. **问题 4 建议尽早推进**——浏览器独立化改动极小（新增容器 + 改一个环境变量），但直接决定内存是否可控，是投入产出比很高的一项。
6. **问题 8 建议单独立项优先修复**——它独立于本方案，且严重性不低于本方案要解决的问题。
7. 问题 5、7 可并行推进（实例上限与快照能力预期，均不阻塞开工）。
